# 售前、POC 与解决方案

## 1. 售前的角色

售前连接销售、产品、技术和客户业务，目标不是“演示功能”，而是把客户问题转成可验证方案，并降低客户对价值、技术、实施和采购的风险。

## 2. 售前主流程

```text
机会识别
→ Discovery
→ 需求澄清
→ 方案设计
→ Demo
→ 技术验证
→ POC/Pilot
→ Proposal/RFP
→ 商务支持
→ 交付移交
```

## 3. Discovery 输出

售前需要确认：

- 客户业务流程和目标；
- 当前系统/设备/数据；
- 核心痛点与影响；
- 必选能力和可选能力；
- 集成、数据、安全与合规要求；
- 用户规模、负载和性能；
- 部署方式；
- 预算与时间；
- 决策标准；
- 验收方式。

输出应是“问题—目标—需求—方案假设”，不是客户原始需求列表的简单抄写。

## 4. Solution Architecture

解决方案至少包含：

- 业务场景；
- 用户与角色；
- 产品模块；
- 数据流；
- 系统集成；
- 部署架构；
- 权限与安全；
- 实施范围；
- 边界和排除项；
- 成功指标。

## 5. Demo 设计

高质量 Demo 应围绕客户场景，而不是按菜单逐项展示。

```text
客户问题
→ 关键任务
→ 产品操作
→ 可量化结果
→ 与现状对比
```

Demo 前应确认观众角色，不同角色关注点不同：管理层看价值与风险，用户看效率，IT 看架构和集成。

## 6. POC 何时需要

POC 适合验证高风险假设，例如：

- 技术能否达到关键指标；
- 数据能否接入；
- AI 准确率是否满足业务；
- 设备能否适配现场；
- 流程是否能跑通。

不应把 POC 变成免费定制项目。

## 7. POC Charter

POC 开始前必须定义：

- Business Question；
- Scope；
- Success Criteria；
- Data/Input；
- Environment；
- Timeline；
- Customer Owner；
- Vendor Owner；
- Resource；
- Exclusion；
- Exit Decision。

POC 结束必须形成 Go / No-Go / Conditional Go，而不是无限延长。

## 8. Pilot 与 POC 的区别

- POC：证明能力可行；
- Pilot：在有限真实业务范围内验证上线价值和运营方式；
- Production：正式规模化部署。

## 9. RFI / RFP / RFQ

- RFI：了解供应商和方案能力；
- RFP：围绕需求征集完整方案；
- RFQ：重点比较明确规格下的报价。

收到 RFP 后应先做 Bid/No-Bid 判断：战略价值、胜率、资源投入、产品匹配、价格竞争、关系基础和交付风险。

## 10. 招投标

核心能力：

- 资格文件；
- 商务偏离表；
- 技术偏离表；
- 技术方案；
- 项目计划；
- 服务与 SLA；
- 报价；
- 案例与资质；
- 投标风险审查。

不要为了投标承诺产品和交付团队无法实现的指标。

## 11. ROI / TCO

售前需要帮助客户比较：

```text
Current TCO
vs
Future TCO + New Value
```

TCO 可包括采购、实施、集成、人工、维护、停机、库存、云资源、培训和切换成本。

## 12. 交付移交

签约后必须从售前向项目/客户成功团队移交：

- 客户目标；
- 承诺范围；
- 关键联系人；
- 架构；
- POC 结果；
- 风险；
- 特殊条款；
- 验收标准；
- 未解决事项。

销售阶段的隐性承诺如果没有移交，会在交付期爆雷。

## 13. AI 在售前中的应用

可用于 RFP 解析、历史方案检索、需求映射、架构初稿、Demo 脚本、POC 结果分析和知识问答。涉及性能、合规、交付和价格承诺的内容必须人工审核。
